# doc-protocol 审查 —— handoff 在长期开发中的肥大问题

- 日期：2026-10-05
- 对象：`skills/doc-protocol/SKILL.md`（217 行）对「交接文档长期膨胀」的治理能力
- 取证：`D:\Code\stock-agent` 实况（git 史 + 文档 + 源码 `/d/IDE/ZCode/resources/glm/zcode.cjs`）
- 状态：**只读审查，未改动任何代码或配置。**

---

## 0. 结论

**协议的归档条款是一个真出口，但它是"跑步机"，不是收敛器。**

单位是「每越线搬一次家」，而产出速率恒定 ⇒ 体量呈**锯齿增长**（归档砍一半 → 再涨回来），
稳态下永远是「刚归完档 → 6 天后又超线」。

更要紧的是：**决定上下文税的三个"每次必读"载体里，有两个完全没有体量约束** ——
**待办账本**和**指令文件**。而账本恰好是协议明写「永不归档」的那一个。

一句话根因：

> **协议治的是「同一事实多处抄写」（横向分裂），没治「单一载体无限追加」（纵向膨胀）。**

| 膨胀类型 | 协议是否覆盖 |
|---|---|
| 横向：同一事实多处抄写、计数漂移 | ✅ 治（单一权威载体 + 红灯 1/4） |
| 纵向 - 会话段区 | ⚠️ 只搬不蒸（红线「归档 ≠ 改写」，**总量不减**） |
| 纵向 - **待办账本** | ❌ **无出口**（明写「账本永不随段归档」） |
| 纵向 - **指令文件** | ❌ 无预算（只有第三节「准入测试」，无字节约束） |
| 纵向 - 归档产物自身 | ❌ 无上限（只规定「v 号递增」） |

### 1.2 待办账本 —— 唯一无出口的载体（**本条最严重**）

| 指标 | 实测值 |
|---|---|
| 位置 / 行数 | 第 7~66 行 / 60 行 |
| 体量 | **91,355 B = 全文的 14.1%** |
| 数据行 | 42 行 |
| 其中已划掉（`~~`） | **25 行 = 60% 死行** |
| 无状态符号（不合第四节词表） | 9 行 |
| 行均 / 单行峰值 | **2,175 B** / 5,249 B |

两个问题叠加：

1. **死行永久驻留。** 第四节要求「完成行当轮划掉并注提交号（**可复查**）」，
   第五节红线又规定「**账本永不随段归档**」。
   但「可复查」这个理由**不成立** —— 可复查性已由 git 提供（`git show <sha>` 即可复查，
   这正是第二节「git + 测试 = 唯一真值」的立场）。表里保留死行**不增加任何可复查性**，是纯负债。
   更糟的是划掉的行会**越积越多**：完成率越高，死行越多。
2. **2000 行阈值对 60 行的表完全无感。** 账本没有任何体量约束，
   却在以 **2.2 KB/行** 的速度单调增长。

**外推**：若每天新增 1.5 条待办、完成率 60%，则账本 ≈ **一年 +1.2 MB** ——
超过今天整个 handoff.md（648 KB）。即：**账本会先于段区成为新的不可读块。**

## 2. 根因分析

协议的三条主规则各自都对，但覆盖的膨胀面只有一部分：

1. **横向（多处抄写）** —— 治得好。这是 E1/E4/E5/E9 的靶心，单一权威载体 + 红灯 1/4 是有效机制。
2. **纵向（单一载体追加）** —— 只治了段区，而且是「搬」不是「减」：
   - 第五节红线明确「归档 ≠ 改写」，所以 `handoff.md` + `docs/archive/*` 的**总量单调增长**。
   - 账本被**明写排除**在归档之外（「账本永不随段归档」）—— 这条在 E2 的语境下是对的
     （防的是账本被活埋 / 被误搬），但它**顺带把账本变成了唯一无出口的载体**。
3. **阈值单位错配** —— 唯一阈值是「**2000 行**」，但真正决定「读不读得动」的是**字节**：
   - 全文 317 B/行、账本 2,175 B/行、AGENTS.md 384 B/行；
   - 最长单行 5,249 B —— **一行顶 2.5 个普通行**，行数阈值对此完全无感。
4. **全靠自律，无机械闸** —— 所有阈值（2000 行 / 6 周 / 补记 ≤3）都只写在收尾清单里，
   没有脚本或守卫测试。实测结果：**三个阈值全部处于「已越线但未执行」状态。**

## 3. 建议（按性价比排序，均为待决，未实施）

### R1 —— 给账本加出口（最高性价比）

完成行**不再永久驻留**：划掉后经过**一个归档周期**，移出活表。
- 形态 A：迁入当期归档文件（`docs/archive/handoff-archive-v{N}.md` 末尾加一节「本期已结账」）。
- 形态 B（更保守）：表内**只保留最近 N 行已完成项**（如 10 行），更早的移出。
- 论据：可复查性由 git 提供，此举零信息损失，却直接砍掉 60% 的行与同等比例字节。

### R2 —— 阈值改双判据，并覆盖账本

- `handoff.md` 归档线：`2000 行` **或** `500 KB`（取先到者）。
- **账本单列预算**：如 `≤ 15 KB`，超限即按 R1 清理。这是当前**完全缺失**的一环。

### R3 —— 补记上限机械化

「补记 ≤3」写成一条可跑的检查（该仓库已有守卫测试文化，可挂 `scripts/` 或既有守卫）；
或至少进收尾清单的自查命令清单。

### R4 —— 单行软上限

账本「说明」列与段内单行设软上限（如 **≤ 600 B**），超长内容移入 `docs/`，表内留指针。
治的是「字节密度」这个行数阈值看不见的维度。

### R5 —— 机械化体量检查（把自律换成闸）

写一个 `scripts/check-doc-budget.py`：输出各文档行数/字节、账本大小、归档线是否越线、
补记是否超限，退出码非零即红。**证据：三个阈值全部「越线未执行」，说明纯自律不成立。**
（可与 `docs/plans/project-guardrails-entrypoints-task-2026-10-04.md` 的 SessionStart 注入合流：
开场直接把「账本 N KB / handoff N 行 / 已越线」打进上下文。）

### R6 —— 指令文件字节预算 + 周期性重估

- 给指令文件设硬预算（如 `≤ 60 KB`，留 40% 余量对抗回弹）。
- 超限必须抽叙事 —— **先例已有**（`docs/architecture/41-agents-narrative-extraction-round2-2026-10-02.md`，84,565 B），
  缺的只是「周期性重估」这一步：现在只在「有人想起来」时才做，做完 3 天回弹。
- 建议把「指令文件字节 + 余量」纳入 R5 的检查输出，让回弹在越线前就被看见。

## 6. 给决策者的一句话

**协议不缺规则，缺「闸」。** 三个阈值（2000 行 / 6 周 / 补记 ≤3）**全部越线未执行**，
账本与指令文件**各自没有阈值** —— 而这两样正是每会话都要读的东西。
最小可行修法 = **R1（账本出口）+ R2（账本字节预算）+ R6（指令文件字节预算）**；
根治 = 加 **R5** 把它们变成跑得起来的检查。
