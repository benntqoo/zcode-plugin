# evidence — 每条规则对应的事故模式

本文件回答「协议为什么长这样」。修订规则前先读这里；新增规则时在此追加依据。

下列是**通用失效模式**（从真实事故抽象而来，已去掉具体数字与项目名 —— 具体实证属于各仓库的
**落地档**；本技能内已带一份实例：[`stock-agent.md`](stock-agent.md)）。规则来源列指向 `SKILL.md` 的节。

## E1 进度真值分裂 —— 「无法对齐实际进度」的病根

同一进度事实同时维护在 **5+ 个载体**里，各自漂移：日志段正文、外部缓存记忆、agent 记忆、
专门的核查文档、已退役文件的批注。

后果实例：为回答「处置到底做到哪了」，不得不专门新写一份核查文档 —— 而**该核查文档自己
又被复查揪出多处计数错误**。两层教训：
**进度账本分裂逼出核查文档；核查文档自己又变成新的分裂面。**

→ 规则来源：第一节「git+测试=唯一真值」、红灯 3/4/7、第四节待办账本模式。

## E2 待办账本被「新段前插」活埋 —— 直接机制

交接文档头部**声明**本文含「活追踪表」，表真实存在且结构健康，但它位于第 1819 行：
建表时在顶部附近，此后 50+ 个新段不断从文件顶前插，把它推到 55 段之下。
新会话从顶部读，**永远到不了那里** —— 待办实质丢失。

这是「承诺的表存在但没人看得见」的**结构性**缺陷，不是维护缺失。

→ 规则来源：第四节「表钉顶、新段插入点＝表紧后方」、第五节插入点条款。

## E3 段落 / 补记结构失效

- 某段累积 **43 条补记**横跨 4 天，同段内混杂事故、修复、拍板、新待办。
- 另一段单日 10 条补记，深夜续会话不断追加。
- 「还剩什么」埋在段中部，第 25~35 行以下即不可扫读。

→ 规则来源：第五节「段=战役单元 ≤1 天、补记 ≤3、跨日必新段、结果先行段头」。

## E4 数字多处漂移

- 同一规模数字出现 **4 个版本**（spec 实测 vs README vs 退役文件 vs 记忆），
  其中 README 自称「以 spec 实测为准」却**同段复制了具体数值**。
- 文件行数上限被三批「更正」批注覆盖，而真值其实由守卫测试冻结 —— **测试才是真值，prose 复述必过期**。

→ 规则来源：第二节「计数只允许 文件名+命令+日期 式引用」、第三节「不复述上限数值」。

## E5 欠账散文记账

- 日志各段用散文记「本会话 N 个提交均未 push」。
- 记忆记着多个互不一致的欠账数字（11 / 59 / 66）。
- git 实况：**0** —— 所有散文数字均已过期。

→ 规则来源：第六节真值命令、红灯 3、「段内只记本段产出 N 提交这种不过期的事实」。

## E6 结论迁移通道淤塞

- 四条新不变量滞留在日志与测试 docstring，长期未迁入指令文件。
- 头部承诺「结论固化后迁入」，但迁移靠人记、**无收尾清单兜底**，于是没人迁。

→ 规则来源：第三节准入测试、第七节收尾清单第 5 步、红灯 5。

## E7 指令文件职责漂移（上下文税）

指令文件除不变量外携带：完整事故叙事（带日期的根因链）、运维史、操作细节。
它**每个会话自动注入** —— 叙事越长，每会话上下文税越高，而真正「不读会做错事」的
规则密度被稀释。

→ 规则来源：第三节「不读会做错事才进」、形态「规则+一句归因+指针」、红灯 6。

## E8 死文档死而不僵

某文件最后一次实质更新在数月前，职责已被里程碑史 + 守卫测试 + 日志三方接管，
**残留价值只是一份历史快照**。但它留在根目录持续吸引「更正」批注，成为数字漂移的固定污染源。

→ 规则来源：第一节「已退役文档：墓碑指向新真值源，不再更新」。

## E9 协议自身多副本

「多文档分工」全文同时存在于：日志头部、agent 记忆、外部缓存记忆 —— 各自演进。
**用户裁定**：外部应用缓存不是文档面，不纳入协议管辖；协议管辖的副本一律改为指针。

→ 规则来源：第九节「skill 是唯一规范源，管辖副本改指针」、第一节外部缓存条款。

## E10 日志无归档出口 → 无限膨胀

诊断时日志 3742 行 / 154 段；此后 18 天**翻倍**。机制 = 里程碑蒸馏欠账
（十七个战役日仅蒸馏 6 条，结论滞留段内不迁）+ 协议只有「旧段不回改」而**没有出口**。

裁决：老段**逐字**迁 `docs/archive/`，**不倒进里程碑史**（里程碑史只收蒸馏结论，
收日志 = 换个文件继续肥）。段号指针依赖以「归档文件段头原样保留」保持可解析。

→ 规则来源：第一节 归档 行、第五节归档条款、第七节收尾清单第 4 步。

## E11 外部缓存被当状态源

外部应用生成的缓存目录（`.workbuddy/` 等）被当作进度 / 状态源引用，但**不保证更新、
不保证与代码同步**。它偶尔「抓出」过真问题，但那属于巧合，**不构成依赖理由**。

→ 规则来源：第一节 外部应用缓存目录 条款。

## 维护约定

- 新增规则 → 在对应 E 条追加「→ 规则来源」，或新开一条。
- 规则的**具体实证**（项目名、数字、文件路径）留在**该项目的落地档**里（实例：
  [`stock-agent.md`](stock-agent.md)），不进本文件 —— 本文件只留可复用的失效模式。
